# HowToLiveBetter-Local

> 🌐 **在线版：<https://libin-opoo.github.io/HowToLiveBetter-Local/>**
> （手机、平板都能直接打开；也可双击本地 `index.html` 离线使用）


《[高性价比人生指南](https://github.com/eternity4719/HowToLiveBetter)》的本地镜像 + 结构化数据抽取 + 本地检索页。

| `tools/check_layout.py` | 布局测试：在 12 档屏幕宽度下检查横向溢出 |
| `tools/check_search.py` | 功能测试：搜索、分类筛选、证据等级排序共 23 项断言 |

| `使用说明.md` | 面向使用者的说明：打开方法、操作指南、维护说明 |

## 自动同步与版本管理

```bash
python3 tools/sync_upstream.py --check    # 只看上游有没有更新
python3 tools/sync_upstream.py            # 同步 + 提交 + 推送
python3 tools/sync_upstream.py --no-push  # 只提交
python3 tools/sync_upstream.py --rollback 1.0.0
```

一次同步的顺序：浅克隆上游 → 和 `sync-state.json` 里的 commit 比对 → 变了才继续 →
替换 `upstream/` → 重跑抽取 → 比对新旧数据算出增删改 → 版本号自增 →
备份旧 `data.json` 到 `backups/` → 重建 `index.html` → 更新 `sync-state.json` → 提交 → 推送。

- **幂等**：上游没变就直接退出，不产生空提交。
- **失败不落地**：任何一步出错都不会提交，仓库保持原样。
- **只动自己的文件**：`git add` 只针对 `upstream/ data.json index.html sync-state.json`，
  不会把你其他的本地改动一起提交。
- **版本号**：有条目增删升中间位（`1.0.0`→`1.1.0`），只是内容修订升末位（`1.0.0`→`1.0.1`）。
- **提交备注**自动写明版本号、上游 commit、条目数变化和具体改了哪几条。
- **备份**放 `backups/`，只留最近 20 份，**不进 Git**（GitHub 上的提交历史本身就是
  每个版本 `data.json` 的备份，那份更长久）。

Windows 定时任务（每天 + 登录时）：

```powershell
powershell -ExecutionPolicy Bypass -File tools\install-sync-task.ps1
powershell -ExecutionPolicy Bypass -File tools\install-sync-task.ps1 -Remove
```

> 本文件里的 `.ps1` 必须存成 **UTF-8 with BOM**：Windows PowerShell 5.1 在没有 BOM 时
> 按系统 ANSI 读取，中文会被拆坏并报语法错误。另外 `-AtLogOn` 触发器不加 `-User`
> 会报 Access is denied，要显式指定当前用户。

## data.json 字段

| 字段 | 含义 | 对应正文 |

| `备注` | 附加说明（附加字段） | `- 备注：` |
| `源文件` | 来源文件路径（附加字段） | — |
| `条目编号` | `章节序号-条目序号`，如 `1-3`（附加字段） | — |

## index.html 页面说明

全部用原生 JavaScript 实现，未引入任何第三方库。

### 配色模式

- 顶部搜索框右侧有一个按钮，循环切换 **自动 → 浅色 → 深色**，按钮上直接显示当前模式。
- **自动**跟随系统 `prefers-color-scheme`；系统配色变了会立刻跟着变。
- 选择记在 `localStorage`（键 `htlb.theme`）；**只在用户主动切换时才写**——
  每次加载都写一遍会在 `file://` 下触发同步磁盘写，实测拖慢首屏。
- 主题在 `<head>` 里的一小段脚本中提前定好，避免深色模式打开时先闪一下白底。
- 深色不是简单反色：所有文字色都按 **WCAG AA**（正文 4.5:1、大号文字 3:1）选过，
  由 `tools/check_theme.py` 对页面上每一处文字实测验证。

### 快捷键

| 按键 | 作用 |
| --- | --- |
| `Ctrl+K` / `Cmd+K` | 聚焦搜索框并全选（会拦掉浏览器自带搜索栏） |
| `Esc` | 清空搜索内容；搜索本来就空时，顺手取消分类筛选 |

搜索框右侧有 `Ctrl K` / `⌘ K` 的提示，按平台自动切换。

### 搜索

- **匹配范围**：只匹配 `data.json` 的 `标题`、`内容`、`所属主题` 三个字段（常量 `SEARCH_FIELDS`）。
  刻意不搜 `成本 / 收益 / 备注 / 来源出处`，否则会命中卡片收起状态下看不见的文字，
  看起来像「搜出来的东西不含关键词」。
- **模糊匹配**：大小写不敏感的子串匹配；关键词按空白拆开，多个词之间是 **AND**（都命中才算）。
  例如「血压 筛查」= 两个词都出现。
- **实时响应**：`input` 事件触发，带 120ms 防抖；命中的关键词用 `<mark>` 高亮，
  且搜索时摘要的行数上限从 2 行放宽到 4 行，让命中的位置更容易露出来。
- 高亮只用 DOM 节点（`createTextNode` / `<mark>`）拼接，不经过 `innerHTML`，没有注入风险。

### 分类筛选

- 横向滚动的分类导航，目前放了「健康 / 金钱 / 职场」3 个分类；点一下筛选，**再点一下取消**，回到全部。
- 分类与章节主题的映射写在 `CATEGORIES` 常量里（`index.html` 与 `tools/build_index.py` 内各一份），
  34 个章节主题当前已全部归入这 3 类，改这一处即可调整。当前口径：健康 17 个主题 / 327 条，
  金钱 10 个主题 / 210 条，职场 7 个主题 / 113 条。
- 搜索与分类可以叠加，两者是交集关系。

### 排序

- **所有结果都按证据等级排序：A → B → C**，默认视图也一样。
- 同一等级内保持 `data.json` 的原始顺序（用「原始下标 + 等级」显式做稳定排序，
  不依赖引擎的 `Array.prototype.sort` 是否稳定）。
- 等级取值含 `A（争议）`、`B（指南强推荐，但底层证据等级低）` 这类带括号的写法，按首字母归类。
- 状态栏右侧固定标注「按证据等级 A→C 排序」。

### 加载

打开就能看到内容，不等网络：

- 首屏**先用内嵌数据同步渲染**，然后再去取外部 `data.json`。取回来内容和内嵌副本一致时
  完全不重渲染（比条数 + 首尾标题的指纹），省掉一次重建 650 张卡片的开销；
  不一致（比如你手动改了 `data.json`）才换成新数据。
- 数据请求失败（`file://` 直接双击）时只是把页脚的数据来源标成「内嵌快照」，不影响内容。

> 曾经试过「先渲染 24 张、剩下的分片补齐」，用 `tools/check_perf.py` 实测后**回退了**：
> 分片之间浏览器要对整个网格重新布局，650 张的整体渲染从 ~220ms 涨到 ~478ms（2 倍多），
> 而首屏并没有真的提前。一次布局比多次便宜得多。

### 卡片

- 默认展示全部 650 条；每条是卡片，点击（或聚焦后按 Enter/空格）展开 `成本 / 收益 / 备注 / 来源出处`。
- 展开内容按需渲染，首屏只渲染标题与摘要。
- **配色与适配**：浅蓝 + 白色，纯 CSS；≥780px 两列、以下单列；已测 320–1920px 无横向溢出。

### 本地数据导入导出

页面底部有两个按钮，全程在浏览器里完成，不发起任何网络请求。

- **导出数据**：把当前正在使用的数据打包成 `data.json` 下载（Blob + `a[download]`），
  导出内容与 `data.json` 是同一份序列化格式，可以直接覆盖项目里的同名文件。
- **导入数据**：选一个 JSON 文件，校验通过后替换页面正在使用的数据，并自动按证据等级重排。
- **校验规则**：顶层必须是数组；每条必须是对象且含 7 个必填字段
  （`标题/内容/所属主题/成本/收益/证据等级/来源出处`），值必须是非空字符串；
  `证据等级` 必须以 A/B/C 开头。任一条不合格就整份拒绝，列出前 5 个问题，**不改动现有数据**。
- **数据去向**：导入的数据写进浏览器 `localStorage`，刷新或重新打开仍在；
  此时底部会出现「恢复内置数据」，一键清掉导入内容、还原内置数据。
- 启动优先级：本机导入的数据 > `data.json` > 内嵌快照。

> **关于「替换本地的 data.json」**：浏览器出于安全限制，无法直接改写磁盘上的文件，
> 所以「导入」替换的是**页面正在使用的数据**（保存在本机浏览器里）。
> 要让磁盘上的 `data.json` 也更新，导入后点「导出数据」，用下载到的文件覆盖项目里的 `data.json`。
> 另外注意：双击打开的页面读的是**内嵌快照**，覆盖了 `data.json` 之后，
> 需要重跑 `python3 tools/build_index.py` 重新内嵌，或者用 `python3 -m http.server` 起服务让页面读外部文件。

### 打开方式

- **直接双击**：`file://` 下浏览器会拦截 `fetch`，页面自动回退到构建时内嵌的**全量** 650 条数据，
  搜索和筛选照常可用（页脚会标注「内嵌快照」）。
- **本地起服务**（读取外部 `data.json`）：

  ```bash
  python3 -m http.server 8000
  # 打开 http://127.0.0.1:8000/index.html
  ```

## 测试

需要本机装有 Edge/Chrome。

### 布局测试

```bash
python3 tools/check_layout.py                      # 默认 320 / 360 / 375 / ... / 1920 共 12 档
python3 tools/check_layout.py --widths 320,768,1440
python3 tools/check_layout.py --browser /path/to/msedge
```

脚本把 index.html 放进一个可调宽度的 iframe 里逐档测量（无头浏览器在 Windows 上有约 496px 的
最小窗口宽度，直接用 `--window-size` 测不到 320/375 这类手机宽度）。检查项：页面横向溢出、
元素越界、视口是否按预期生效。

### 搜索与筛选功能测试

```bash
python3 tools/check_search.py
```

用真实事件驱动搜索框和分类按钮，跑 23 项断言，覆盖：默认全量与排序、单关键词命中、
命中项确实含关键词、来源/备注不再命中、多关键词 AND、清空恢复、分类筛选与取消、
状态栏选中态、搜索与分类叠加、无结果提示、复位。

### 导入导出功能测试

```bash
python3 tools/check_io.py
```

跑 32 项断言，覆盖：按钮存在、**导出内容与 `data.json` 逐字符相同**、下载文件名与类型、
合法导入后数据被替换并能原样导出、6 类非法文件（非 JSON / 顶层非数组 / 空数组 /
元素非对象 / 缺字段 / 证据等级非法）都被拦下且不破坏现有数据、导入后重新打开页面仍在、
「恢复内置数据」能还原并清空存储。

> 脚本会拦下 `anchor.click`，只验证导出的 Blob 内容与下载配置，不在测试里真的落盘
> ——无头模式下真实下载会让浏览器挂住。真实落盘可以用 CDP 单独验证（见提交说明）。

### 配色对比度测试

```bash
python3 tools/check_theme.py
```

把 `index.html` 复制三份（浅色 / 深色 / 跟随系统），分别在 `<head>` 里强制指定配色，
然后按 WCAG 2.1 的相对亮度公式，算出**每一处可见文字**与其实际背景的对比度并判定是否达标。
深色那一份还会先展开一张卡片、搜一次关键词，把 `成本/收益/备注/来源` 和 `<mark>` 高亮也纳入检查。
另外会验证主题按钮的循环切换、`localStorage` 写入、以及 `auto` 是否真的跟随系统。

### 自动同步测试

```bash
python3 tools/check_sync.py
```

在临时沙箱里把整个仓库复制一份，造一个「有新提交」的假上游（新增 1 条 + 修改 1 条），
跑完整同步流程后断言 33 项：条数变化、新条目的 7 个字段、原有条目一条没丢、
未改动条目逐字未变、备份内容等于同步前的 `data.json`、版本号与历史、`index.html` 重建、
上游快照替换、提交备注内容、工作区干净、幂等、回滚、以及上游不可用时不留下烂摊子。

### 加载性能检查

```bash
python3 tools/check_perf.py
```

在 `<head>` 装探针（劫持 `fetch` 记录请求返回时刻，用 MutationObserver 记录首张卡片进入 DOM 的时刻），
分别在 `file://` 和本地 `http://` 两种打开方式下测量，判定**首张卡片是否早于数据请求返回**。

> 绝对毫秒数在这类共享机器上波动很大（同一版本实测能在 198~294ms 之间跳），
> 所以主判据是「首卡是否早于数据返回」这个次序关系，不是单个数字。
